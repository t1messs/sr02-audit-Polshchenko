# Розділ 4. План рефакторингу з пріоритезацією «вигода / ризик»

**Вигода (В), 1–5** — наскільки крок полегшить подальшу роботу (5 — знімає щоденний біль,
1 — косметика). **Ризик (Р), 1–5** — імовірність зламати поведінку (1 — перейменування
локальної змінної, 5 — зміна ієрархії, покрита одним тестом). **Т** — оцінка часу, хв.
**Індекс** = В ÷ Р; сортування — за спаданням індексу, за рівних індексів вище менш
трудомісткий крок.

## 4.3. Правила безпеки

1. **Один рефакторинг — один коміт.** Змішувати рефакторинг зі зміною поведінки заборонено;
   зміна поведінки — лише окремий коміт `fix:` або `change:` із записом у журналі рішень.
2. **Крок довший за 20 хвилин розбивається на менші** — кроки 14 і 20 виконуються
   послідовністю виділень по одному методу, але фіксуються одним комітом лише після зелених
   тестів.
3. **Після кожного кроку — `dotnet build` і `dotnet test`.** Коміт робиться тільки при 53
   зелених тестах і нульовій кількості помилок складання.
4. **Якщо тести червоні понад 10 хвилин — `git checkout .`** і крок починається спочатку
   меншими порціями.
5. **Спочатку кроки з низьким ризиком:** видалення мертвого коду, константи, змінні — вони
   скорочують і прояснюють код, тож наступні кроки ризикують менше.
6. **Очікувані значення в тестах не змінюються ніколи.** Файл тестів змінюється лише тоді,
   коли змінилася сигнатура (перейменування), і кожна така зміна пояснюється в журналі рішень.
7. **Повідомлення коміту:** `refactor(Клас): Rxx що зроблено` — код рефакторингу з каталогу
   на початку суті, до 72 символів.
8. **Публічний API не змінюється без запису в журналі рішень** — видалення публічного
   прапорця `UseZoneQueue` і перейменування `count_waiting` — рішення Р-02 і Р-03.
